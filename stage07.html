COURSE 01 · STAGE 07

第一课 · 第 7 阶段：模型诊断——数据偏差、标签偏差、分布漂移、OOD 与数据污染

从“会训练模型”进入“会诊断模型”：效果不好时，先判断错误来自数据、标签、切分、分布、模型、优化还是部署，而不是立刻换大模型。

DiagnosisData BiasLabel NoiseDriftOODContamination

一、第 7 阶段总地图：Diagnosis before Optimization

前六阶段我们已经知道如何定义 X/Y、训练、评价和设计数据。第 7 阶段真正解决的是：

模型做不好时，到底应该改什么？

一个错误可能来自至少七层：

Data → Label → Split → Distribution → Model → Optimization → Deployment
现象可能真正原因
医疗设备技术参数漏报医疗数据覆盖不足
专家答案前后矛盾标签噪声 / 标注标准不统一
离线好、线上差分布漂移 / 测试污染 / 处理链路不一致
同项目 Test 得分异常高Project Leakage
新政策后能力下降Concept Drift
陌生专业项目高置信度乱答OOD + 校准问题
专家的第一反应：

一个错误现象 ≠ 一个唯一原因。先定位根因，再决定加数据、修标签、加 RAG、换模型还是调训练。

二、Data Bias：模型永远存在“经验边界”

假设训练集共 100,000 条，但分布如下：

IT           70,000
办公用品      15,000
物业           8,000
医疗设备       4,000
工程           2,000
其他           1,000

总体 Recall 可能达到 92%，医疗设备却只有 63%。这不一定说明模型“不会推理”，更可能说明医疗采购经验明显不足。

Sampling Bias：采样偏差

如果风险案例主要从“投诉处理决定”生成，模型看到的是 P(X | 投诉项目)，但上线面对的是 P(X | 全部采购项目)。它可能学会投诉项目特有的语言，而不是真正的风险规律。

Representation Bias：代表性偏差

中央级数据很多、县级很少；IT 很多、医疗很少；公开招标很多、特殊采购方式很少——都会让“政府采购模型”实际上只精通某一部分政府采购。

不要只问“ProcurementLM 会不会政府采购”，而要问：它在哪些分布中经过验证？
Model Envelope（能力包络）示例：
时间：2023–2026
对象：货物 / 服务为主
地区：中央、省、市数据充分
行业：IT、物业、医疗较多
风险：资格、参数、评分常见风险覆盖充分
边界：极特殊工程/科研采购覆盖有限

三、Label Bias / Label Noise：标签不是天然真理

如果真实风险案例被错误标成无风险，那么模型预测正确时反而会被 Loss 惩罚：

错误 Label → 错误 Loss → 错误 Gradient → 错误 Parameter Update

专家分歧本身也是数据

例如同一评分条款：

专家 A：高风险
专家 B：需结合项目规模
专家 C：中风险

任务本身可能具有不确定性。强制压成单一 0/1 标签，会损失重要信息。更成熟的数据可以保存专家投票、争议等级和条件化结论。

核心认知：

Ground Truth 并不总等于 Absolute Truth。它通常是当前专家体系对现实的最佳测量。

模型与专家不一致时的三种结果

  1. 模型错 → 进入 Hard Negative / Hard Positive。
  2. 专家错 → 修正 Label。
  3. 双方都有合理依据 → 标记 Borderline / Ambiguous。

因此专业数据生产必须包含复核（Adjudication）流程。

四、Distribution Shift：上线世界不是静止的

P_train(X,Y) ≠ P_deploy(X,Y)

1. Covariate Shift

P(X) 变化，但 P(Y|X) 大体稳定。例如训练时 IT 占 70%，部署时医疗占 60%。

2. Label Shift

P(Y) 变化。例如行业规范改善后风险条款比例从 20% 降到 5%，原先阈值可能不再合适。

3. Concept Drift

P(Y|X) 本身变化。这对政府采购最重要：新法规、新政策、新监管口径可能让“同一个 X”在不同时间得到不同 Y。

Y = f(X, time, jurisdiction, applicable_rules)

因此法规知识库至少应跟踪：

document_id
title
jurisdiction
publish_date
effective_date
expiry_date
status
supersedes
superseded_by
模型是某一时刻数据分布的快照，不是永久有效的真理容器。

五、OOD：模型碰到“自己没见过的世界”怎么办？

OOD = Out-of-Distribution。比如训练主要覆盖 IT、物业、办公、医疗，突然遇到非常特殊的科研设施采购：极专业参数、安全要求和稀有履约场景都远离训练分布。

X_new ∉ typical(P_train(X))

危险：模型不一定会主动说“我不会”

大型语言模型即使面对 OOD，也可能继续生成非常流畅、非常自信的答案。

Fluent Answer ≠ In-Distribution ≠ Reliable Answer

Abstention / Selective Prediction

成熟专业系统应允许：

当前项目与已验证分布差异较大
缺少足够相似历史案例
法规证据不足
模型不确定性较高
→ 转人工专家复核
可靠 ProcurementLM 的能力应包含：
Predict + Estimate Uncertainty + Detect OOD + Abstain

“知道什么时候不该自动回答”本身就是专业能力。

六、Data Contamination：测试集被污染，会制造虚假的安全感

Exact Duplicate

Train 和 Test 出现完全相同条款，答对几乎不能证明泛化能力。

Near Duplicate

“注册资本不得低于5000万元”与“注册资金至少为人民币五千万元”文字不同但语义几乎相同。

Project Leakage

同一个采购项目：
招标文件 → Train
质疑答复 → Train
投诉决定 → Test

文件不同，但答案关系已经泄漏。因此政府采购数据往往要以 Project 而不是 Document 作为隔离单元。

Template / Organization Leakage

同一代理机构高度重复模板随机拆到 Train/Test，模型可能学的是机构模板而非业务规律。更严格测试应尝试跨机构、跨模板、跨地区泛化。

Future Leakage

在“采购文件发布时预测风险”的任务里，如果输入包含后续更正公告、投诉结果、中标结果，就是用未来预测过去。

最危险的后果：False Confidence。

模型本来一般，但被污染的 Test 得分极高，团队因此误以为已经达到上线标准。

七、Spurious Correlation / Shortcut Learning：模型可能“答对但理由错”

模型可能利用与业务无关的信号：机构名称、模板页眉、某些关键词、文件格式等。

Counterfactual Test：反事实测试

只改变一个因素，观察输出是否异常变化：

原句：供应商须在本市注册 → Risk 0.95
只改：本市 → 项目所在地 → Risk 0.20

如果语义核心没有大幅变化，模型却剧烈改变，可能说明它依赖某个表面词。

Perturbation Test：扰动测试

保持语义不变，改写措辞：

注册资本不得低于5000万元
≈ 实缴资本应达到人民币五千万元以上

如果性能大幅下降，说明模型过度依赖词面。

保留关键词，改变语义

采购文件不得以供应商注册资本作为不合理限制条件。

如果模型只看到“注册资本”仍判高风险，说明学到了 Keyword，而不是 Semantic Meaning。

八、ML Diagnosis：用分层诊断代替“炼丹”

第一层：Train / Validation

TrainValidation优先怀疑
差差数据、标签、模型容量、优化
好差过拟合、分布差异
好好继续验证真实部署
差好评估流程/数据异常

第二层：Slice Evaluation

Overall Recall = 90%
资格 = 96%
评分 = 92%
技术 = 68%
  └─ IT 技术 = 90%
  └─ 医疗技术 = 52%
      └─ 明显案例 = 92%
      └─ 边界案例 = 37%

这样把“模型不行”定位成“医疗技术参数边界案例能力不足”。

第三层：Confidence × Correctness

正确错误
高置信度稳定能力最高价值错误
低置信度边界/不确定相对预期错误

第四层：人工 Root Cause Review

对 100 个 FN 做归因：

输入缺上下文    28%
Label 问题      19%
医疗知识缺失    24%
真正推理错误    16%
法规更新         8%
其他             5%
只有 16% 真的是“模型脑子不够聪明”——直接换 70B 很可能治不了其余 84%。

九、完整政府采购诊断案例：从“客户说医疗漏报多”到根因

  1. 发现症状：ProcurementLM V0.3 总体 Recall=91%，但医疗客户反馈漏报明显。
  2. Slice：医疗 Recall=61%，确认不是主观感受。
  3. 继续切片：资格 90%、评分 82%、技术参数 42%。
  4. 查 Train Distribution：20,000 条技术参数数据里，医疗只有 700 条。
  5. 审错题：大量涉及专用设备兼容、临床使用场景、特殊市场供应。
  6. 根因判断：主要是 Data Coverage Gap，而不是模型容量。
  7. 修复：补医疗 Hard Positive、Hard Negative、市场竞争案例和专家标注。
  8. 重新训练：医疗技术参数 Recall 从 42% → 79%。
这就是 Diagnosis-driven Training：先定位，再动手。

另一个典型：判断正确、法规引用错误

如果风险判断 95%，Citation Accuracy 只有 61%，优先优化 RAG：法规切分、metadata、时效/地区过滤、Retriever、Reranker，而不是反复 Fine-tune 风险分类器。

十、Error Taxonomy：错误必须可归因

未来 ProcurementLM 不应该只记录 correct=false。建议至少保留：

{
  "task": "technical_requirement_review",
  "prediction": "no_risk",
  "ground_truth": "risk",
  "confidence": 0.94,
  "error_type": "false_negative",
  "root_cause": "domain_coverage_gap",
  "domain": "medical_device",
  "difficulty": "hard_positive",
  "ood_score": 0.81,
  "label_review": "confirmed",
  "recommended_action": "add_training_examples"
}

系统级错误可以归入：

DataLabelKnowledgeReasoningRetrievalRuleOODDeployment
成熟系统必须能够回答：Why did this fail?

十一、本阶段 5 个专家核心心智模型

  1. 模型有经验边界：不是简单问“会不会”，而是问“在哪些分布里会”。
  2. 标签只是现实的测量：专家也会错，专家分歧本身也是数据。
  3. 模型是数据分布的快照：业务、法规和数据变化都会造成 Drift。
  4. 可靠系统必须知道自己不会：OOD 检测、不确定性和 Abstention 很重要。
  5. 先诊断再优化：Error Analysis 决定应改数据、标签、知识、模型还是系统。
模型表现差，不要先问“换什么模型”，先问“错误来自哪一层”。

十二、从“炼丹”进入科学实验：Hypothesis → Experiment → Measurement

不要一次同时改模型、LR、数据、Batch、Prompt、Loss 和 RAG。否则指标从 78% 涨到 85%，你仍然不知道为什么。

更科学的实验：

Experiment A：只增加 Hard Negative
Experiment B：只增加医疗数据
Experiment C：只换 14B
Experiment D：只优化 RAG
→ 比较 ΔMetric
Hypothesis → Controlled Experiment → Measurement → Diagnosis → Next Hypothesis

例如提出假设：

H1：

“医疗技术参数表现差，主要因为医疗训练数据覆盖不足。”

然后只补相应数据并复测。如果 Slice Recall 显著提高，假设得到支持；如果没有，就继续寻找其他根因。

最终认知：

机器学习研发越来越像科学实验。能力提升来自“提出可验证的原因假设，然后用控制实验确认”，而不是随机试参数。
